# Kimi 使用规范

## 语言要求

**重要：Kimi 在与用户交互时必须使用中文**

### 规则说明

1. **思考过程使用中文**
   - 分析问题时使用中文思考
   - 规划解决方案时使用中文思考
   - 内部推理过程使用中文

2. **回答问题使用中文**
   - 所有回复内容必须使用中文
   - 代码注释使用中文
   - 技术说明使用中文
   - 错误提示使用中文

3. **例外情况**
   - 代码本身（变量名、函数名等）可以使用英文
   - 技术术语在必要时可以保留英文原文，但需要附带中文解释
   - 引用的英文文档或错误信息可以保持原文，但需要提供中文翻译

### 示例

✅ **正确示例**：
```
我正在分析这个问题...（思考过程）

根据您的需求，我建议采用以下方案：
1. 首先优化数据库查询
2. 然后重构代码结构
3. 最后添加单元测试

代码示例：
// 优化后的查询方法
public List<User> findUsers() {
    // 实现逻辑
}
```

❌ **错误示例**：
```
I'm analyzing this problem...

Based on your requirements, I suggest:
1. First optimize database queries
2. Then refactor code structure
3. Finally add unit tests
```

## 交互原则

- 保持专业、准确、友好的中文表达
- 使用清晰的中文技术术语
- 在必要时提供中英文对照
- 确保中文表达的准确性和流畅性



## 版本管理

- 如果项目使用git管理，需要自动将本次新增的文件添加到暂存区，不要commit
- .gitignore文件需要忽略
- 未经允许不得进行commit、push操作




## 代码修改记录规则

**重要：每次修改代码业务时必须记录变更内容**

### 记录流程

1. **编码前阅读**: 每次开始编码前，必须先阅读 `./.claude/docs/TEMP.md` 了解已有的业务逻辑变更
2. **修改后记录**: 每次修改代码业务后，将修改内容记录到 `./.claude/docs/TEMP.md`
3. **交叉整理**: 如果新的业务逻辑与原有记录有交叉或关联，需要整理后更新 `./.claude/docs/TEMP.md`

### 记录格式

- 每条记录用**一句话**简要总结修改内容即可，不需要详细展开
- 格式示例：`## 2026-05-26 新增策略模式演示（支付场景，strategy 包下）`



## 编码规范

**重要：所有代码必须遵循阿里巴巴编码规范**

### 规范要求

1. **命名规范**
   - 类名使用 UpperCamelCase 风格（大驼峰）
   - 方法名、参数名、成员变量、局部变量使用 lowerCamelCase 风格（小驼峰）
   - 常量命名全部大写，单词间用下划线隔开
   - 抽象类命名使用 Abstract 或 Base 开头
   - 异常类命名使用 Exception 结尾
   - 测试类命名以它要测试的类名开始，以 Test 结尾

2. **代码格式**
   - 缩进使用 4 个空格，禁止使用 Tab 字符
   - 单行字符数限制不超过 120 个
   - 左大括号前不换行，左大括号后换行
   - 右大括号前换行，右大括号后还有 else 等代码则不换行
   - if/for/while/switch/do 等保留字与括号之间都必须加空格

3. **注释规范**
   - 类、类属性、类方法的注释必须使用 Javadoc 规范（Java）或对应语言的文档注释规范
   - 所有的抽象方法（包括接口中的方法）必须用 Javadoc 注释
   - 方法内部单行注释，在被注释语句上方另起一行，使用 // 注释
   - 所有的枚举类型字段必须要有注释，说明每个数据项的用途

4. **OOP 规范**
   - 避免通过一个类的对象引用访问此类的静态变量或静态方法
   - 所有的覆写方法，必须加 @Override 注解
   - 相同参数类型，相同业务含义，才可以使用可变参数
   - 外部正在调用或者二方库依赖的接口，不允许修改方法签名，避免对接口调用方产生影响

5. **集合处理**
   - 判断所有集合内部的元素是否为空，使用 isEmpty() 方法，而不是 size() == 0
   - 在使用 java.util.stream.Collectors 类的 toMap() 方法转为 Map 集合时，一定要注意当 value 为 null 时会抛 NPE 异常
   - ArrayList 的 subList 结果不可强转成 ArrayList

6. **并发处理**
   - 获取单例对象需要保证线程安全，其中的方法也要保证线程安全
   - 创建线程或线程池时请指定有意义的线程名称，方便出错时回溯
   - 线程资源必须通过线程池提供，不允许在应用中自行显式创建线程
   - 线程池不允许使用 Executors 去创建，而是通过 ThreadPoolExecutor 的方式

7. **控制语句**
   - 在一个 switch 块内，每个 case 要么通过 break/return 等来终止，要么注释说明程序将继续执行到哪一个 case 为止
   - 在 if/else/for/while/do 语句中必须使用大括号
   - 在高并发场景中，避免使用"等于"判断作为中断或退出的条件
   - 表达异常的分支时，少用 if-else 方式，应该先判断异常情况并提前返回

8. **异常处理**
   - Java 类库中定义的可以通过预检查方式规避的 RuntimeException 异常不应该通过 catch 的方式来处理
   - 异常不要用来做流程控制，条件控制
   - catch 时请分清稳定代码和非稳定代码，稳定代码指的是无论如何不会出错的代码
   - 捕获异常是为了处理它，不要捕获了却什么都不处理而抛弃之

9. **数据库规范**
   - 不得使用外键与级联，一切外键概念必须在应用层解决
   - 禁止使用存储过程，存储过程难以调试和扩展，更没有移植性
   - 数据订正（特别是删除、修改记录操作）时，要先 select，避免出现误删除
   - in 操作能避免则避免，若实在避免不了，需要仔细评估 in 后边的集合元素数量

10. **安全规范**
    - 隶属于用户个人的页面或者功能必须进行权限控制校验
    - 用户敏感数据禁止直接展示，必须对展示数据进行脱敏
    - 用户输入的 SQL 参数严格使用参数绑定或者 METADATA 字段值限定，防止 SQL 注入
    - 用户请求传入的任何参数必须做有效性验证

### 适用语言

虽然阿里巴巴编码规范主要针对 Java，但其核心原则适用于所有编程语言：
- **Java**: 完全遵循《阿里巴巴 Java 开发手册》
- **JavaScript/TypeScript**: 参考核心原则，结合 ESLint 规范
- **Python**: 参考核心原则，结合 PEP 8 规范
- **Go**: 参考核心原则，结合 Go 官方规范
- **其他语言**: 参考核心原则，结合该语言的最佳实践
